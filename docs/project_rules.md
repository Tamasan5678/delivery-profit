# Delivery Profit V2 開発ルール

## 1. 基本方針

- 仕様を優先する。
- 既存コードを尊重する。
- 必要最小限の変更を行う。
- 勝手な仕様変更は禁止する。
- リファクタリングは依頼がある場合のみ行う。

## 2. 開発手順

### 作業前

1. `README.md` を読む。
2. `docs` フォルダを確認する。
3. 現在の実装内容を理解する。
4. 不明点は推測せず報告する。

## 3. 実装ルール

- 依頼内容以外を変更しない。
- 不要なリネームを行わない。
- 不要な削除を行わない。
- `README.md` を変更しない。
- ファイル構成を勝手に変更しない。

## 4. コード品質

実装後は可能な限り、次のコマンドを実行する。

```bash
flutter analyze
```

エラーがある場合は、原因と影響を報告する。

## 5. エミュレーターテスト

Android Emulator が利用可能な場合は、次を確認する。

- アプリ起動
- 対象機能の動作確認
- 画面遷移
- クラッシュの有無
- ログの確認

重大なログがある場合は報告する。

## 6. バグ修正

不具合を発見した場合は、次を説明する。

- 原因
- 修正内容
- 影響範囲

仕様変更が必要な場合は、勝手に変更せず報告する。

## 7. 設計書更新

仕様が変更された場合は、`docs` の設計書も更新する。設計書と実装に差異がある場合は、差異を明示して確認する。

## 8. Gitルール

コミット前に `git diff` を確認し、不要な変更が含まれていないことを確認する。

## 9. 報告

作業の最後に、必ず日本語で次を報告する。

- 変更ファイル
- 変更内容
- テスト結果
- 未確認事項
- 今後の改善案

## 10. Delivery Profit 専用ルール

- HomeScreen は通常モードと配達中モードを切り替える。
- 配達中画面を新規作成しない。
- `DeliverySession` を中心に設計する。
- 現在はメモリ管理とする。
- 将来 SQLite へ移行する。
- `docs` を正しい仕様書として扱う。
- コードより先に設計書を確認する。

## 11. 画面サイズと向き

- Delivery Profitはスマートフォンでの片手操作性を重視し、縦画面のみを正式対応とする。横画面はサポート対象外であり、横画面未確認はリリース阻害事項としない。
- UI品質の最低基準は画面幅360dpとし、360dp、411dp、480dpの3幅で確認する。360dpでRenderFlex overflow、文字切れ、主要ボタンの画面外配置が発生しないことを必須とする。
- 360dpを最小、411dpを標準、480dpを大型スマートフォンの確認幅とする。新規画面と既存UI変更もこの3幅を確認する。
- 文字サイズ拡大時も主要操作を可能にし、すべてを初期表示内へ収められない場合は縦スクロールで到達可能にする。
- 固定高さ・固定幅へ過度に依存せず、Row内の文字と数値には必要に応じてFlexible、Expanded、FittedBox等を使用する。
- 操作内容に必要な画面、Dialog、BottomSheetは360dpでも主要操作へ到達できる構成にする。
